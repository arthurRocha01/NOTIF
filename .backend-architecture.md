# Backend Architecture — NOTIF

## Stack

| Camada | Tecnologia |
|---|---|
| Framework | NestJS v11 + TypeScript |
| ORM | Prisma v6 |
| Banco de dados | PostgreSQL |
| Autenticação | JWT (passport-jwt) + bcrypt |
| Push notifications | Firebase Admin SDK (FCM) |
| Validação | class-validator + class-transformer |
| Documentação | Swagger (`/api`) |
| Deploy | Vercel (handler serverless em `src/main.ts`) |

---

## Padrão Arquitetural

Clean Architecture + DDD. Cada módulo segue a mesma estrutura de camadas:

```
modules/<feature>/
  domain/          — entidade, interface do repositório, tipos
  application/     — service (casos de uso)
  infrastructure/  — repositório impl (Prisma), mapper, FCM
  presentation/    — controller HTTP
  dto/             — DTOs de entrada e saída
```

## Modelos de domínio (Prisma schema)

### `Sector`
```
id, name (unique), createdAt, updatedAt
→ tem N Users, N Notifications
```

### `User`
```
id, name, email (unique), passwordHash?, role (EMPLOYEE|SUPERVISOR|ADMIN), fcmToken?
→ pertence a 1 Sector (obrigatório)
→ tem N NotificationAssignments
```

### `Notification`
```
id, title, message (Text), level (LOW|MEDIUM|HIGH|CRITICAL)
slaMinutes, requiresAcknowledgment (default true)
sectorId? (null = global; preenchido = setorial)
authorId → User
→ tem N NotificationAssignments
```

### `NotificationAssignment`
```
id, userId, notificationId
status: PENDING | VIEWED | ACKNOWLEDGED | OVERDUE
createdAt, dueAt?, deliveredAt?, viewedAt?, acknowledgedAt?
UNIQUE(userId, notificationId)
```

---

## Máquina de estados de `NotificationAssignment`

```
                 ┌──────────────────────────────┐
PENDING ─────────►  VIEWED  ────────────────────► ACKNOWLEDGED
   │                  │
   └──────────────────┴──► OVERDUE  (dueAt expirou, não ACKNOWLEDGED)
```

| Método | Efeito |
|---|---|
| `markAsDelivered(slaMinutes)` | Sets `deliveredAt = now`, `dueAt = now + slaMinutes` |
| `markAsViewed()` | Sets `viewedAt`, status → `VIEWED` (se não OVERDUE ou ACKNOWLEDGED) |
| `markAsRecognized()` | Sets `acknowledgedAt`, status → `ACKNOWLEDGED` |
| `checkOverdue(now)` | Status → `OVERDUE` se `dueAt < now` e não `ACKNOWLEDGED` |
| `isBlocking()` | `true` se `CRITICAL` e não `ACKNOWLEDGED` |
| `getResponseTimeInMs()` | `acknowledgedAt - deliveredAt` em ms (ou null) |

## Autenticação

- **Guard global**: `JwtAuthGuard` aplicado em todas as rotas via `APP_GUARD`
- **Bypass**: decorator `@Public()` marca rotas públicas
- **Dev bypass**: `DISABLE_AUTH=true` injeta usuário fake `{ userId, email }` em `req.user`

### JWT Payload
```ts
{ sub: string, email: string }
// Após validação: req.user = { userId: string, email: string }
```

### Rotas públicas
- `POST /auth/login`
- `POST /users`
- `POST /sectors`

### Notifications
| Método | Rota | Auth | Descrição |
|---|---|---|---|
| GET | `/notifications` | JWT | Lista todas as notificações |
| GET | `/notifications/:id` | JWT | Busca por ID |
| POST | `/notifications` | JWT | Cria notificação |
| PATCH | `/notifications/:id` | JWT | Atualiza `title` e/ou `requiresAcknowledgment` |
| DELETE | `/notifications/:id` | JWT | Remove notificação |

**Body criação:**
```json
{
  "title": "string (5-100 chars)",
  "message": "string (10-2000 chars)",
  "level": "LOW | MEDIUM | HIGH | CRITICAL",
  "slaMinutes": "int (>= 1)",
  "requiresAcknowledgment": "boolean (opcional, default true)",
  "sectorId": "uuid (opcional — null = global)",
  "authorId": "uuid (opcional — TODO: extrair do JWT)"
}
```

**Efeito colateral ao criar (sectorId preenchido):**
1. Cria um `NotificationAssignment` com `status=PENDING` para cada usuário do setor
2. Envia push FCM via multicast para todos os tokens do setor
3. Remove FCM tokens inválidos retornados pelo Firebase

**Response:**
```json
{
  "id": "uuid",
  "title": "string",
  "message": "string",
  "level": "LOW | MEDIUM | HIGH | CRITICAL",
  "slaMinutes": "int",
  "requiresAcknowledgment": "boolean",
  "sectorId": "uuid | null",
  "authorId": "uuid",
  "createdAt": "Date"
}
```

### Assignments — Leitura e Admin
| Método | Rota | Auth | Descrição |
|---|---|---|---|
| GET | `/assignments` | JWT | Lista **todos** os assignments |
| GET | `/assignments/mine` | JWT | Lista assignments do usuário autenticado (via JWT) |
| GET | `/assignments/:id` | JWT | Busca assignment por ID |
| GET | `/assignments/user/:userId` | JWT | Lista assignments **pendentes de entrega** (`deliveredAt == null`) do userId |
| DELETE | `/assignments/:id` | JWT | Remove assignment |

> **Atenção de roteamento**: `/assignments/mine` deve aparecer antes de `/assignments/:id` no controller para não ser capturado como parâmetro dinâmico. Atualmente está correto no código.

**Diferença entre `findAllByUserId` e `findByUserId`:**

| Método do repositório | Filtro | Usado em |
|---|---|---|
| `findAllByUserId(userId)` | Todos os assignments do usuário | `GET /assignments/mine` |
| `findByUserId(userId)` | Apenas `deliveredAt == null` | `GET /assignments/user/:userId` e `POST /assignments/sync/:userId` |

**Response:**
```json
{
  "id": "uuid",
  "userId": "uuid",
  "notificationId": "uuid",
  "notificationLevel": "LOW | MEDIUM | HIGH | CRITICAL",
  "status": "PENDING | VIEWED | ACKNOWLEDGED | OVERDUE",
  "createdAt": "Date",
  "dueAt": "Date | null",
  "deliveredAt": "Date | null",
  "viewedAt": "Date | null",
  "acknowledgedAt": "Date | null"
}
```

### Assignments — Interações
| Método | Rota | Auth | Descrição |
|---|---|---|---|
| POST | `/assignments/sync/:userId` | JWT | Sincroniza entregas pendentes do userId |
| POST | `/assignments/:assignmentId/view` | JWT | Marca como visualizado |
| POST | `/assignments/:assignmentId/acknowledge` | JWT | Confirma ciência |

**`POST /assignments/sync/:userId`**
- Busca assignments com `deliveredAt == null` do `userId`
- Para cada um: chama `markAsDelivered(slaMinutes)` e persiste
- Retorna: `{ message: string, deliveredCount: number }`

**`POST /assignments/:assignmentId/view`**
- Extrai `userId` do JWT (`req.user.userId`)
- Valida que o assignment pertence ao usuário (403 se não)
- Chama `markAsViewed()`
- Retorna: `{ message: string }`

**`POST /assignments/:assignmentId/acknowledge`**
- Extrai `userId` do JWT (`req.user.userId`)
- Valida propriedade (403 se não for dono)
- Chama `markAsRecognized()`
- Retorna: `{ message: string }`

## FCM / Push Notifications

Dois serviços existem no codebase:

| Serviço | Arquivo | Status | Credenciais |
|---|---|---|---|
| `FcmService` | `notifications/infrastructure/fcm.service.ts` | **Ativo** (usado pelo NotificationService) | `applicationDefault()` |
| `FirebaseService` | `firebase/firebase.service.ts` | **Legado** (não injetado em lugar algum) | Env vars explícitas |

**Bug conhecido em `FcmService.retriveFalideTokens`**: o método sempre retorna `[]` em vez de `failures`, portanto tokens inválidos nunca são removidos.

## Variáveis de Ambiente

| Variável | Obrigatória | Descrição |
|---|---|---|
| `DATABASE_URL` | Sim | URL de conexão Prisma (pooled) |
| `DIRECT_URL` | Sim | URL direta ao banco (migrations) |
| `JWT_SECRET` | Sim | Chave de assinatura do JWT |
| `JWT_EXPIRES_IN` | Sim | Expiração do token (ex: `"7d"`) |
| `DISABLE_AUTH` | Não | `"true"` para bypass de auth em dev |
| `FIREBASE_PROJECT_ID` | Não | Usado pelo `FirebaseService` (legado) |
| `FIREBASE_CLIENT_EMAIL` | Não | Idem |
| `FIREBASE_PRIVATE_KEY` | Não | Idem |

Para `FcmService` (ativo), as credenciais Firebase são obtidas via `applicationDefault()` — geralmente `GOOGLE_APPLICATION_CREDENTIALS` no ambiente de produção.

## Validação Global

`ValidationPipe` configurado em modo estrito:
```ts
{ whitelist: true, forbidNonWhitelisted: true, transform: true }
```
- Campos não declarados no DTO são rejeitados (400)
- Transformação automática de tipos primitivos

---

## Deploy

O entry point (`src/main.ts`) exporta um **handler serverless** para Vercel. O app é inicializado de forma lazy (singleton): na primeira requisição cria o app NestJS, nas seguintes reutiliza a instância.

Para rodar localmente, descomentar o bloco `bootstrap()` e comentar o handler.
