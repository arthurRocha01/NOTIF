| Coluna | Tipo | Notas |
|---|---|---|
| `id` | `String (uuid)` | PK |
| `name` | `String` | |

| `role` | `UserRole` | default `EMPLOYEE` |
| `fcmToken` | `String? @db.Text` | Nullable |
| `sectorId` | `String` | FK obrigatória → `sectors.id` |
| `createdAt` | `DateTime` | `@default(now())` |
| `updatedAt` | `DateTime` | `@updatedAt` |

### Entidade de Domínio: `User`
Campos privados idênticos ao Prisma. Métodos mutáveis: `changeName`, `changeFcmToken`, `changePassword`.

> **Atenção:** o domínio não expõe `updatedAt` — `UserResponseDto` também não o inclui.

### `POST /users` — `CreateUserDto`
| Campo | Tipo | Obrigatório | Validações |
|---|---|---|---|
| `name` | `string` | Sim | max 100 |
| `email` | `string` | Sim | email válido |
| `password` | `string` | Sim | min 8, max 50 |
| `sectorId` | `string` | Sim | UUID v4 |
| `role` | `UserRole` | Não | enum válido |
| `fcmToken` | `string` | **Sim** (sem `@IsOptional`) | — |

> **Bug:** `fcmToken` não tem `@IsOptional()` no `CreateUserDto`, portanto é obrigatório na criação mesmo sem validação de não-nulidade formal.

### `PATCH /users/:id` — `UpdateUserDto`
`PartialType(CreateUserDto)` — todos os campos se tornam opcionais, incluindo `password`, `email`, `sectorId` e `role`.

> **Atenção:** o service (`UserService.updateUser`) só processa `name` e `fcmToken`. Campos como `email`, `password` e `sectorId` enviados no PATCH são ignorados silenciosamente (whitelist do DTO não os descarta, mas o service os ignora). `changePassword` existe na entidade e é chamado apenas pelo `AuthService`.

## Assignments

### Prisma: `notification_assignments`
| Coluna | Tipo | Notas |
|---|---|---|
| `id` | `String (uuid)` | PK |
| `userId` | `String` | FK → `users.id` (Cascade delete) |
| `notificationId` | `String` | FK → `notifications.id` (Cascade delete) |
| `status` | `AssignmentStatus` | default `PENDING` |
| `createdAt` | `DateTime` | `@default(now())` |
| `dueAt` | `DateTime?` | Calculado na entrega |
| `deliveredAt` | `DateTime?` | |
| `viewedAt` | `DateTime?` | |
| `acknowledgedAt` | `DateTime?` | |
| UNIQUE | `(userId, notificationId)` | |

> **Importante:** `notificationLevel` e `slaMinutes` **não são colunas da tabela**. O nível é derivado do `JOIN` com `notifications` no momento da leitura (`NotificationAssignmentMapper.toDomain` recebe `PrismaNotification` como segundo argumento).

### Entidade de Domínio: `NotificationAssignment`
Campos privados adicionais (apenas em memória): `notificationLevel`.

**Métodos de ciclo de vida:**
| Método | Efeito |
|---|---|
| `markAsDelivered(slaMinutes)` | `deliveredAt = now`, `dueAt = now + slaMinutes * 60000` |
| `markAsViewed()` | `viewedAt = now`, status → `VIEWED` (se não `OVERDUE` ou `ACKNOWLEDGED`) |
| `markAsRecognized()` | `acknowledgedAt = now`, status → `ACKNOWLEDGED` |
| `checkOverdue(now)` | status → `OVERDUE` se `dueAt < now` e não `ACKNOWLEDGED` |
| `isBlocking()` | `true` se `CRITICAL` e não `ACKNOWLEDGED` |
| `getResponseTimeInMs()` | `acknowledgedAt - deliveredAt` em ms, ou `null` |

### `POST /assignments` — `CreateAssignmentDto`
| Campo | Tipo | Obrigatório | Validações |
|---|---|---|---|
| `userId` | `string` | Sim | UUID v4 |
| `notificationId` | `string` | Sim | UUID v4 |
| `notificationLevel` | `NotificationLevel` | Sim | enum válido |

> **Nota:** Este DTO é para criação manual de assignments. Em produção, assignments são criados automaticamente pelo `NotificationService` ao criar uma notificação com `sectorId`. O `notificationLevel` passado aqui não é persistido (sem coluna no Prisma); é armazenado apenas na entidade em memória e derivado do join nas leituras.

### `PATCH /assignments/:id` — `UpdateAssignmentDto`
`PartialType(CreateAssignmentDto)` — todos opcionais.

### `AssignmentResponseDto`
| Campo | Tipo | Notas |
|---|---|---|
| `id` | `string` | |
| `userId` | `string` | |
| `notificationId` | `string` | |
| `notificationLevel` | `NotificationLevel` | derivado do join |
| `status` | `AssignmentStatus` | |
| `createdAt` | `Date` | |
| `dueAt` | `Date \| null` | |
| `deliveredAt` | `Date \| null` | |
| `viewedAt` | `Date \| null` | |
| `acknowledgedAt` | `Date \| null` | |

> **Typo interno:** o construtor do `AssignmentResponseDto` nomeia o parâmetro `deleviredAt` (typo), mas mapeia corretamente para `this.deliveredAt`. Não afeta a resposta HTTP.

## Fluxo de Mapeamento

```
HTTP Request
    ↓ (ValidationPipe — whitelist: true, forbidNonWhitelisted: true, transform: true)
DTO de entrada (Create/Update)
    ↓ (Service)
Entidade de Domínio (create / reconstitute)
    ↓ (Mapper.toPersistence)
Prisma (banco)
    ↑ (Mapper.toDomain)
Entidade de Domínio
    ↑ (ResponseDto.fromDomain)
DTO de resposta → HTTP Response
```

## Inconsistências Identificadas

| # | Local | Problema |
|---|---|---|
| 1 | `CreateUserDto.fcmToken` | Sem `@IsOptional()` — obrigatório na criação mesmo para usuários sem dispositivo |
| 2 | `UpdateUserDto` | `PartialType` torna `email`, `password`, `sectorId`, `role` opcionais, mas o service ignora todos exceto `name` e `fcmToken` |
| 3 | `CreateNotificationDto.authorId` | `@IsOptional()` — TODO: extrair do JWT; até lá, quem cria deve enviar o `authorId` explicitamente |
| 4 | `UpdateNotificationDto` | `PartialType` permite enviar qualquer campo, mas o service só processa `title` e `requiresAcknowledgment` |
| 5 | `notificationLevel` no assignment | Não é coluna do banco — derivado do JOIN; `CreateAssignmentDto` exige o campo mas ele não é persistido |
| 6 | `AssignmentResponseDto` | Parâmetro do construtor com typo `deleviredAt` (inofensivo — mapeia corretamente) |
| 7 | `Notification` entidade | Campo interno `targetSectorId` vs. getter público `getSectorId()` — nomenclatura inconsistente |
