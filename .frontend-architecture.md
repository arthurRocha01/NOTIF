# Frontend Architecture — NOTIF

## Telas por Role

| Role | Destino | Capacidades |
|---|---|---|
| `ADMIN` | `AdminPanelScreen` | CRUD de Usuários e Setores |
| `SUPERVISOR` | `HomeScreen` | Feed + Dashboard + criar/ver notificações |
| `EMPLOYEE` | `HomeScreen` | Feed + ver/confirmar notificações |

---

## Stack

- **Framework:** Flutter (Dart 3.2+)
- **State Management:** Riverpod 2.5 (`StateNotifierProvider`)
- **HTTP:** `http` package + `ApiClient` próprio
- **Roteamento:** `go_router` 17.1 (incluso mas **não ativo**)
- **Storage local:** `shared_preferences` — integrado para persistência de sessão
- **Charts:** `fl_chart` | **Icons:** `lucide_icons` | **Fonts:** `google_fonts`
- **Push notifications:** `firebase_messaging` ^15.1.3 + `flutter_local_notifications` ^18.0.0
- **Áudio:** `audioplayers` ^6.0.0 — toca `assets/sounds/notice.notif.wav` em alertas críticos

Não usa `go_router`. A navegação é feita manualmente via `IndexedStack` no `HomeScreen`:

```
LoginScreen (authProvider == null)
  ├── AdminPanelScreen (user.isAdmin)
  │     ├── UsersManagementScreen   — CRUD de usuários
  │     └── SectorsManagementScreen — CRUD de setores
  └── HomeScreen (supervisor ou employee)
        ├── [0] FeedContent       — feed social de posts
        ├── [1] DashboardScreen   — monitoramento
        └── [2] AlertAdminScreen  (Supervisor)
              AlertUserScreen     (Employee)
```

Bottom nav adapta-se ao role do usuário. Drawer acessa `AccountScreen` e modais auxiliares.

**`AlertNotifier`** expõe:
- `loadNotifications()` — admin: carrega `GET /notifications`; **guard**: retorna imediatamente se `isLoadingNotifications == true` (evita chamadas duplicadas do `IndexedStack`)
- `loadAssignments()` — employee: carrega `GET /assignments`; **guard**: retorna imediatamente se `isLoadingAssignments == true`
- `createNotification(...)` — admin: `POST /notifications`
- `markAsViewed(assignmentId)` — employee: `POST /assignments/:id/view`; atualiza `status = VIEWED` e `viewedAt = DateTime.now()` localmente

- `markAllPendingAsViewed()` — chama `markAsViewed` para cada assignment PENDING
- `syncDeliveries(userId)` — fire-and-forget
- Token lido automaticamente de `ApiClient.currentToken`

**`SectorNotifier.loadSectors()`** também possui guard: retorna imediatamente se `isLoading == true`.

## Push Notifications (FCM)

**`NotificationService`** (`/core/notifications/notification_service.dart`) — singleton que centraliza FCM e notificações locais:

- `initialize()` — registra handler de background, cria canal Android `notif_alerts_critical` (importância máxima, som `notice_notif.wav`), e wires `onMessage` / `onMessageOpenedApp`
- `showLocalNotification(title, body, id)` — exibe notificação local via `flutter_local_notifications` (uso programático e pelo background handler)
- `onForegroundMessage` / `onNotificationTap` — callbacks configurados por `HomeScreen`
- `getInitialMessage()` — retorna mensagem que abriu o app quando estava fechado
- Guard `_supported`: ativo apenas em Android e iOS; no-op em web/Windows/Linux

**`_backgroundMessageHandler`** (top-level, `@pragma('vm:entry-point')`):
- Mensagens com `notification` field: ignoradas (Firebase já exibe automaticamente pelo sistema)
- Mensagens data-only (sem `notification`): exibe notificação local via `flutter_local_notifications`, usando título/corpo de `message.data`

**Fluxo no `HomeScreen`:**
```
Mensagem FCM recebida (foreground)
  → alertProvider.loadAssignments()              ← recarrega lista e badge
  → level == critical  → _showCriticalOverlay()  → CriticalAlertOverlay (fullscreen, PopScope)
                                                   + _playAlertSound() via audioplayers
  → outros níveis      → _showBanner()            → InAppBannerOverlay (OverlayEntry, auto-dismiss 4s)

Tap na notificação push (onMessageOpenedApp)
  → alertProvider.loadAssignments()              ← recarrega lista e badge
  → level == critical  → _showCriticalOverlay()
  → outros             → navega para aba Alertas (pageIndex = 2)

App iniciado por tap em push (getInitialMessage)
  → mesma lógica do tap
```

**Token refresh automático** (`AuthNotifier._startTokenRefreshListener`):
- Chamado após login e restore de sessão
- Assina `FcmService.onTokenRefresh`; ao receber novo token: chama `PATCH /users/:id` e atualiza `state.fcmToken`
- Subscription cancelada em `logout()` e `dispose()`
- Envolvido em try-catch para não propagar erros em ambientes sem suporte (ex: testes)

**`main.dart`** inicializa Firebase e `NotificationService` antes do `runApp`:
```dart
await Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform);
await NotificationService().initialize();
```

**Badge da navbar** — conta assignments com `status != acknowledged` via `alertProvider`.

## Integração com API

**Base URL:** `https://notifta.vercel.app` — definida em `ApiClient.baseUrl` (único ponto de configuração)

**ApiClient** (`/core/api/api_client.dart`) — classe estática com:
- `static const baseUrl` — URL base usada por todos os services
- Métodos: `get`, `post`, `patch`, `delete`
- Injeta `Authorization: Bearer <token>` automaticamente
- Lança `ApiException(message, statusCode)` em erros
- **Retry com backoff exponencial** para erros `>= 500` (cold start Vercel): 3 tentativas com delays 800ms → 2s → 4s. Erros 4xx e `SocketException` falham imediatamente sem retry. `httpClient` e `retryDelays` são injetáveis para testes.

**Serviços por feature:**

| Serviço | Endpoints usados |
|---|---|
| `AuthService` | `POST /auth/login`, `GET /users/by-email/{email}`, `PATCH /users/:id` (fcmToken, trocar senha com currentPassword, recuperar senha sem currentPassword) |
| `AlertService` | `GET /notifications`, `POST /notifications`, `GET /assignments`, `POST /assignments/:id/view`, `POST /assignments/:id/acknowledge`, `POST /assignments/sync/:userId` |
| `FcmService` | Wrapper de `FirebaseMessaging` — `getToken()`, `onTokenRefresh`. No-op em Windows/Linux (plataformas sem suporte a `firebase_messaging`) |
| `AdminUserService` | `GET /users`, `POST /users`, `PATCH /users/:id`, `DELETE /users/:id` |
| `AdminSectorService` | `POST /sectors`, `PATCH /sectors/:id`, `DELETE /sectors/:id` |
| `PostService` | Mock em memória (sem API real) |

`AuthService` e `AlertService` injetam `http.Client` e `baseUrl` para testabilidade, usando `ApiClient.baseUrl` como padrão.  
Lançam `ApiException` / `AlertServiceException` em erros HTTP e `SocketException`.

## Fluxo de Autenticação

**Login:**
```
LoginScreen
  → AuthService.login(email, password)        → POST /auth/login → JWT
  → ApiClient.setToken(token)                 → armazenado em memória (estático)
  → AuthService.fetchUser(email, token)       → GET /users/by-email/{email}
  → TokenStorage.saveToken(token)             → persistido em SharedPreferences (só após fetchUser)
  → TokenStorage.saveEmail(email)             → persistido em SharedPreferences (só após fetchUser)
  → state = UserModel                         → authProvider atualizado
  → main.dart reage ao authProvider           → redireciona para HomeScreen

  (falha em qualquer etapa) → ApiClient.clearToken() + state = null + errorMessage
```

**Restore de sessão (startup):**
```
main.dart carrega authInitProvider (FutureProvider)
  → AuthNotifier.tryRestoreSession()
      → TokenStorage.getToken() + getEmail()  → lê SharedPreferences
      → se encontrados: AuthService.fetchUser → restaura UserModel no estado
      → ApiException(401)  → clearAll()       → limpa storage (JWT inválido)
      → outros erros (500, SocketException)   → limpa token da memória, PRESERVA storage
                                                 (próxima abertura retenta)
  → authInitProvider completa → main.dart mostra LoginScreen ou HomeScreen
```

`main.dart` observa `authInitProvider` + `authProvider`:
- `authInitProvider.loading` → `CircularProgressIndicator` (splash)
- `user == null` → `LoginScreen`
- `user != null` → `HomeScreen`

**Storage:** `TokenStorage` (`/core/storage/token_storage.dart`) — wrapper injetável de `SharedPreferences`. Chaves: `auth_token`, `auth_email`.

`AuthNotifier` expõe `errorMessage` (String?), `tryRestoreSession()` e `logout()` (limpa token + storage + estado + cancela subscription de token refresh).  
Role `ADMIN` do backend é mapeado para `UserRole.admin` no frontend (não `supervisor`).

## Interceptação de 401

`ApiClient` expõe `static void Function()? onUnauthorized`. Quando `_handleResponse` recebe status 401, chama o callback antes de lançar a exceção. `main.dart` registra `authProvider.notifier.logout()` como handler. `AlertNotifier` também chama o callback diretamente ao capturar `ApiException(statusCode: 401)`.

## Fluxo de Autenticação — Resolução de Setor

Após `fetchUser`, `AuthNotifier` chama `SectorService.getSectors()` e substitui `user.sector` (UUID) pelo nome legível do setor. Fallback silencioso: se a chamada falhar ou o UUID não for encontrado na lista, `user.sector` mantém o valor original.

```
login / tryRestoreSession
  → fetchUser()          → user.sector = UUID
  → getSectors()         → lista de setores
  → firstWhere(id == UUID)
      ↳ encontrado  → user.sector = sectorName  ✓
      ↳ não encontrado / erro → user.sector = UUID (fallback)
```

## Pontos de Atenção

- **`go_router` não ativo** — sem deep linking nem rotas nomeadas.
- **Feed de posts é mock** — `PostService` usa 4 posts hardcoded; `toggleLike()` e `deletePost()` são métodos vazios; `PostModel` sem `fromJson`/`toJson`. Design do feed pendente de melhoria (próxima sprint).
- **`notice_service.dart` vazio** — feature Notices não iniciada.
- **`notificationTitle` / `notificationMessage`** em `AssignmentModel` são opcionais — exibidos quando o backend retornar esses campos embutidos no `GET /assignments`; fallback para `'Notificação'`.
- **`markAsViewed` / `acknowledge`** usam `POST /assignments/:id/view` e `POST /assignments/:id/acknowledge`; status atualizado localmente via `copyWith` após sucesso.
- **`syncDeliveries`** chamado por `AuthNotifier` após login e restore de sessão (`POST /assignments/sync/:userId`).
- **Supervisores recebem assignments** — aba "Minhas notificações" no `AlertAdminScreen` + `DashboardScreen` depende de assignments e setores. `IndexedStack` renderiza ambas as telas simultaneamente; para evitar burst de requisições simultâneas no cold start da Vercel, o carregamento inicial é **centralizado e sequencial no `HomeScreen.initState`**: `await loadNotifications()` → `await loadAssignments()` → `await loadSectors()`. Para supervisores, `markAllPendingAsViewed()` é chamado após `loadAssignments` completar. `DashboardScreen` e `AlertAdminScreen` não disparam cargas no próprio `initState` — apenas expõem `_refresh()` para o botão de atualização manual. Os guards de loading (`isLoadingNotifications`, `isLoadingAssignments`, `isLoadingAssignments`) ainda existem como proteção contra chamadas duplicadas em refresh.
- **`AlertAdminScreen` — abas** — "Painel" (lista de notificações com filtros) e "Minhas notificações" (assignments do supervisor). Aba "Painel" possui dois grupos de chips: (1) nível (`Todos / Baixo / Médio / Alto / Crítico`) com cor dinâmica por `AlertLevel`; (2) setor (chips carregados de `sectorProvider`). Ambos combinados com a busca textual em `_getFilteredAlerts`. `_SectorChip` aceita `selectedColor` opcional para customizar a cor de seleção.
- **Trocar senha** — implementado: valida (min 6 chars, confirmação) e chama `PATCH /users/:id` com `{ currentPassword, password }`. Funciona quando o backend tratar esses campos no `updateUser`.
- **Recuperar senha** — implementado: form com "Nova senha" + "Confirmar" (sem exigir senha atual), chama `PATCH /users/:id` com `{ password }`, exibe tela de sucesso inline. Método `AuthService.updatePassword(userId, newPassword, {currentPassword?})` — `currentPassword` é omitido neste fluxo.
- **`fcmToken`** — integrado com Firebase Messaging. `FcmService` obtém o token após login/restore; `AuthNotifier` atualiza via `PATCH /users/:id` apenas quando difere. Token refresh automático via `onTokenRefresh` stream (subscription gerenciada em `_startTokenRefreshListener`). `AdminUserService.createUser` envia `'fcmToken': null` — backend exige o campo no DTO; usuário criado pelo admin ainda não tem dispositivo registrado. FCM é no-op em Windows/Linux (`_supported` guard).
